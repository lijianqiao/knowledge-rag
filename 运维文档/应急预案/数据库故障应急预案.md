# 数据库故障应急预案

## 1. 覆盖范围

- MySQL 主从集群（订单库、用户库）
- Redis Cluster（缓存与会话）
-  nightly 备份与 PITR 恢复流程

## 2. 常见场景与处置

### 2.1 主库不可用

1. 确认是否为网络闪断还是实例 crash
2. 若确认主库不可恢复：按 runbook 提升从库（需 DBA 授权）
3. 更新应用连接串 / DNS / Proxy 指向新主
4. 验证读写与 replication 状态

```sql
-- 从库晋升前检查
SHOW SLAVE STATUS\G
-- 确认 Executed_Gtid_Set 与主库一致后再操作
```

### 2.2 主从延迟过大（lag > 60s）

1. 检查大事务、DDL、磁盘 IO
2. 必要时 Kill 长查询（需评估业务影响）
3. 读流量临时切到其他从库

### 2.3 Redis OOM

1. `INFO memory` 确认 used_memory 与 maxmemory
2. 短期：扩容或收紧 TTL；禁止未经确认 FLUSHALL
3. 长期：大 key 扫描与 key 规范治理

## 3. 备份恢复

- 全量备份：每日 02:00，保留 7 天
- Binlog：保留 3 天，支持 PITR
- 恢复演练：每半年 1 次，RTO 目标 < 4 小时

## 4. 禁止操作

- 生产库禁止无 WHERE 的 DELETE/UPDATE
- 禁止 peak 时段执行无评审 DDL
- 禁止在故障未评估前强制 failover
